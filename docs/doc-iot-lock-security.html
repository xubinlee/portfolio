安全威胁模型与纵深防御架构

智能门锁作为物理世界与数字世界的交汇点，面临的安全威胁远超普通 IoT 设备。一次成功的攻击不仅意味着数据泄露，更可能导致物理入侵。本篇从传输层加密、身份鉴权、消息防重放、业务风控四个维度，构建纵深防御体系。

通信 TLS 加密

1. mTLS 双向认证架构

门锁设备与 EMQX Broker 之间采用 mTLS（Mutual TLS）双向证书认证，确保通信双方身份可信。与单向 TLS（仅服务端出示证书）不同，mTLS 要求设备也必须出示证书，杜绝伪造设备接入。

CA 私有 PKI 根证书 自建 CA，签发服务端证书与设备客户端证书 信任锚
Srv EMQX 服务端证书 由私有 CA 签发，绑定 Broker 域名/IP 服务端身份
Dev 设备客户端证书 出厂烧录，CN=deviceId，含设备唯一标识 设备身份
CRL 证书吊销列表 丢失/异常设备证书实时吊销，EMQX 定期拉取 吊销机制

TLS 1.3 优势
TLS 1.3 将握手从 2-RTT 缩减到 1-RTT，支持 0-RTT 恢复（会话票证复用），对门锁这种低功耗设备尤为关键。同时移除了 RSA 密钥交换等不安全套件，仅保留 AEAD 加密（AES-GCM / ChaCha20-Poly1305），杜绝 BEAST、POODLE 等降级攻击。

3. 设备证书烧录与轮换

/** 设备证书出厂烧录流程 */
public class DeviceCertBurnService {

    private static final String CA_KEY_PASSWORD = VaultConfig.get("ca.key.password");

    public DeviceCertResult burnDeviceCert(String deviceId, String productModel) {
        // 1. 生成设备 ECC P-256 密钥对（安全芯片内）
        KeyPair keyPair = SecureChip.generateKeyPair("EC", 256);

        // 2. 构建 CSR（Certificate Signing Request）
        X500Name subject = new X500Name(
            "CN=" + deviceId +
            ", O=ISNOWSOFT" +
            ", OU=" + productModel
        );
        PKCS10CertificationRequest csr = CSRBuilder.build(subject, keyPair.getPublic());

        // 3. 私有 CA 签发设备证书（有效期 10 年）
        X509Certificate deviceCert = PrivateCA.signCertificate(
            csr,
            Duration.ofDays(3650),
            KeyUsage.digitalSignature | KeyUsage.keyEncipherment,
            ExtendedKeyUsage.clientAuth
        );

        // 4. 写入安全芯片（私钥不可导出）
        SecureChip.writePrivateKey(deviceId, keyPair.getPrivate());
        SecureChip.writeCertificate(deviceId, deviceCert);

        // 5. CA 证书链一并写入
        SecureChip.writeCACertChain(PrivateCA.getCertChain());

        // 6. 录入设备注册表
        deviceRegistry.register(DeviceCertRecord.builder()
            .deviceId(deviceId)
            .certSerial(deviceCert.getSerialNumber())
            .certFingerprint(HashUtil.sha256Fingerprint(deviceCert))
            .notBefore(deviceCert.getNotBefore())
            .notAfter(deviceCert.getNotAfter())
            .status(CertStatus.ACTIVE)
            .build());

        return new DeviceCertResult(deviceId, "BURNED");
    }
}

4. 证书吊销机制

设备丢失或异常时，需立即吊销其证书，阻止重新接入。采用 CRL + OCSP 双机制：

/** 证书吊销服务 */
public class CertRevocationService {

    public RevocationResult revokeDeviceCert(String deviceId, RevocationReason reason) {
        // 1. 查询设备证书序列号
        DeviceCertRecord cert = deviceCertRepo.findByDeviceId(deviceId);
        if (cert == null) {
            throw new BusinessException("设备证书不存在");
        }

        // 2. 加入 CRL（Certificate Revocation List）
        PrivateCA.addToCRL(cert.getCertSerial(), reason);

        // 3. 更新 OCSP Responder
        ocspResponder.markRevoked(cert.getCertSerial(), reason, Instant.now());

        // 4. 强制设备下线（踢出 MQTT 连接）
        emqxAdminApi.kickClient(deviceId);

        // 5. 更新设备注册表状态
        cert.setStatus(CertStatus.REVOKED);
        cert.setRevokedAt(Instant.now());
        cert.setRevocationReason(reason);
        deviceCertRepo.save(cert);

        // 6. 记录审计日志
        auditLog.record(AuditEvent.builder()
            .action("CERT_REVOCATION")
            .target(deviceId)
            .detail("reason=" + reason + ", serial=" + cert.getCertSerial())
            .build());

        return new RevocationResult(deviceId, "REVOKED");
    }
}
CRL vs OCSP
CRL（证书吊销列表）：CA 定期发布被吊销证书列表，EMQX 定期拉取。延迟取决于拉取间隔。OCSP（在线证书状态协议）：实时查询证书状态，延迟更低。生产环境建议OCSP Stapling（服务端主动附带 OCSP 响应），避免客户端直接查询 OCSP 服务器带来的隐私泄露和性能瓶颈。

设备 Token 鉴权

1. 双层 Token 架构

设备鉴权采用 激活 Token + 访问 Token 双层设计，与 mTLS 形成互补：

层次机制用途生命周期
L1 传输层mTLS 证书设备身份证明 + 通道加密10 年（出厂烧录）
L2 应用层激活 Token设备首次激活凭证一次性（激活后失效）
L3 应用层访问 Token日常通信鉴权24h（可刷新）
L4 业务层MQTT ACLTopic 订阅/发布权限与 Token 同步

2. 挑战-应答式激活

设备首次上电时，通过挑战-应答（Challenge-Response）机制完成激活，避免激活凭证在网络中明文传输：

/** 设备激活 — 挑战应答流程 */
public class DeviceActivationService {

    public ActivationResult activate(ActivationRequest request) {
        // 1. 验证设备证书（mTLS 已完成，从连接上下文获取）
        String deviceId = MtlsContext.getClientCN();

        // 2. 生成随机挑战码（32字节）
        String challenge = SecureRandomUtil.hex(32);

        // 3. 缓存挑战码，等待设备应答（有效期 60s）
        challengeCache.put(deviceId, challenge, 60, TimeUnit.SECONDS);

        return new ActivationResult(deviceId, challenge);
    }

    public TokenPair verifyAndIssueToken(ChallengeResponse response) {
        String deviceId = response.getDeviceId();
        String cachedChallenge = challengeCache.get(deviceId);

        // 1. 校验挑战码有效性
        if (cachedChallenge == null) {
            throw new SecurityException("挑战码已过期");
        }

        // 2. 用设备公钥验签应答
        // 设备端：sign = ECC_Sign(privateKey, challenge)
        boolean valid = EccUtil.verifySignature(
            deviceCertRepo.getPublicKey(deviceId),
            cachedChallenge,
            response.getSignature()
        );
        if (!valid) {
            throw new SecurityException("签名验证失败");
        }

        // 3. 销毁挑战码（一次性）
        challengeCache.invalidate(deviceId);

        // 4. 签发访问 Token 对
        TokenPair tokens = tokenService.generateDeviceToken(deviceId);

        // 5. 更新设备激活状态
        deviceRepo.updateStatus(deviceId, DeviceStatus.ACTIVATED);

        return tokens;
    }
}

3. MQTT ACL 权限控制

Token 鉴权通过后，EMQX 基于 ACL 规则限制设备的 Topic 订阅/发布权限，实现最小权限原则：

/** EMQX HTTP ACL 回调 — 设备权限校验 */
@RestController
@RequestMapping("/mqtt/acl")
public class MqttAclController {

    @PostMapping("/check")
    public AclResult checkAcl(@RequestBody AclRequest req) {
        String clientId = req.getClientId();
        String topic = req.getTopic();
        String action = req.getAction(); // subscribe | publish

        // 1. 从 Redis 获取设备 ACL 规则
        DeviceAclRule rule = redisTemplate.opsForValue()
            .get("device:acl:" + clientId);

        if (rule == null) {
            return AclResult.deny();
        }

        // 2. 校验 Topic 匹配规则
        //    设备只能订阅/发布自己 ID 下的 Topic
        boolean allowed = rule.getPatterns().stream()
            .anyMatch(pattern -> {
                // 允许: /hotel/lock/{deviceId}/#
                // 禁止: /hotel/lock/{otherDeviceId}/#
                String expected = "/hotel/lock/" + clientId + "/";
                return topic.startsWith(expected)
                    && rule.getAllowedActions().contains(action);
            });

        return allowed ? AclResult.allow() : AclResult.deny();
    }
}

/** ACL 规则示例 */
// 设备 LOCK-001 允许的 Topic：
//   SUB  /hotel/lock/LOCK-001/up/#     — 上报数据
//   SUB  /hotel/lock/LOCK-001/down/#   — 接收指令
//   PUB  /hotel/lock/LOCK-001/up/#     — 发布状态
//   PUB  /hotel/lock/LOCK-001/down/resp — 指令应答
// 禁止：
//   任何其他设备的 Topic
//   /hotel/gateway/# 网关级 Topic
//   /hotel/lock/+/down/cmd  跨设备指令
最小权限原则
ACL 规则遵循默认拒绝 + 白名单放行策略。设备只能操作 /hotel/lock/{自己的ID}/ 下的 Topic，无法订阅其他设备数据，也无法发布到网关级 Topic。即使 Token 泄露，攻击者也无法操控其他设备。

防重放攻击

1. 重放攻击场景

攻击者截获一条合法的开锁指令，在稍后重新发送，试图再次开锁。如果服务端无法识别这是"旧消息"，门锁将被非法打开。

场景 A：指令重放
截获 /down/cmd 开锁指令，原样重发
场景 B：上报重放
截获设备上报消息，伪造重复事件
场景 C：激活重放
截获激活应答，重复激活伪造设备

2. Nonce + 时间戳方案

每条消息携带递增序列号（Nonce）和时间戳（Timestamp），服务端校验两者来识别重放：

/** 消息防重放校验器 */
public class ReplayDefenseService {

    private static final long MAX_TIMESTAMP_DRIFT_MS = 30_000; // 30秒

    public ReplayCheckResult checkMessage(MqttMessage message) {
        MessagePayload payload = JSON.parseObject(message.getPayload(), MessagePayload.class);

        // 1. 时间戳校验 — 拒绝过期消息
        long now = System.currentTimeMillis();
        long drift = Math.abs(now - payload.getTimestamp());
        if (drift > MAX_TIMESTAMP_DRIFT_MS) {
            return ReplayCheckResult.reject("TIMESTAMP_EXPIRED",
                "消息时间戳偏差 " + drift + "ms 超过阈值");
        }

        // 2. Nonce 唯一性校验 — Redis SETNX 原子去重
        String nonceKey = "nonce:" + payload.getDeviceId() + ":" + payload.getNonce();
        boolean isNew = redisTemplate.opsForValue()
            .setIfAbsent(nonceKey, "1", MAX_TIMESTAMP_DRIFT_MS, TimeUnit.MILLISECONDS);

        if (!isNew) {
            return ReplayCheckResult.reject("NONCE_DUPLICATE",
                "重复 Nonce: " + payload.getNonce());
        }

        // 3. 序列号单调递增校验（设备维度）
        String seqKey = "seq:" + payload.getDeviceId();
        Long lastSeq = redisTemplate.opsForValue().get(seqKey);
        if (lastSeq != null && payload.getSeq() <= lastSeq) {
            return ReplayCheckResult.reject("SEQ_REGRESSION",
                "序列号回退: last=" + lastSeq + ", current=" + payload.getSeq());
        }

        // 4. 更新最新序列号
        redisTemplate.opsForValue().set(seqKey, payload.getSeq(), 7, TimeUnit.DAYS);

        return ReplayCheckResult.accept();
    }
}

/** 消息载荷结构 */
{
    "deviceId": "LOCK-001",
    "nonce":    "a3f8c2e1d9",       // 随机数（防重放）
    "seq":      10247,               // 递增序列号
    "timestamp": 1722672000000,      // 毫秒时间戳
    "signature": "MEUCIQ...",        // ECC 签名

3. 消息签名验证

即使 Nonce 和时间戳都合法，仍需验证消息签名，确保消息未被篡改：

/** 消息签名校验 */
public class MessageSignatureVerifier {

    public VerifyResult verify(SignedMessage msg) {
        // 1. 构建签名原文 = deviceId + nonce + seq + timestamp + payloadHash
        String signingContent = String.join("|",
            msg.getDeviceId(),
            msg.getNonce(),
            String.valueOf(msg.getSeq()),
            String.valueOf(msg.getTimestamp()),
            HashUtil.sha256Hex(msg.getPayloadJson())
        );

        // 2. 获取设备公钥
        PublicKey devicePublicKey = deviceCertRepo
            .getPublicKey(msg.getDeviceId());

        // 3. ECC-P256 签名验证
        boolean valid = EccUtil.verify(
            devicePublicKey,
            signingContent.getBytes(StandardCharsets.UTF_8),
            Base64.getDecoder().decode(msg.getSignature())
        );

        if (!valid) {
            // 签名失败 → 记录安全事件
            securityEventService.record(SecurityEvent.builder()
                .type("SIGNATURE_INVALID")
                .deviceId(msg.getDeviceId())
                .detail("签名验证失败，可能消息被篡改")
                .severity(SecuritySeverity.HIGH)
                .build());
        }

        return valid ? VerifyResult.ok() : VerifyResult.fail("签名不匹配");
    }
}
三层防重放
第一层：时间戳 — 拒绝超过 30s 的过期消息；第二层：Nonce + Seq — Redis SETNX 原子去重 + 序列号单调递增校验；第三层：签名 — ECC-P256 确保消息完整性和来源真实性。三层叠加，即使攻击者获取了合法消息，也无法在有效窗口内重放成功。

非法开锁风控拦截

1. 风控模型设计

风控系统在业务层对开锁行为进行实时评估，拦截异常开锁请求。核心思路：规则引擎 + 评分模型，在开锁指令下发前完成风险判定。

L1 实时规则引擎 硬规则：时间/频率/地点/身份 → 直接拦截 毫秒级
L2 评分模型 多维度评分：设备/用户/环境 → 风险等级判定 准实时
L3 离线分析 行为基线建模：历史模式 → 异常检测 + 模型更新 T+1

2. 实时规则引擎

/** 开锁风控规则引擎 */
public class UnlockRiskEngine {

    private final List<RiskRule> rules = List.of(
        // R1: 异常时段开锁（酒店场景：凌晨 2:00-5:00）
        new TimeWindowRule(2, 5, RiskLevel.MEDIUM),

        // R2: 短时间高频开锁（5分钟内超过 5 次）
        new FrequencyRule(5, 5, TimeUnit.MINUTES, RiskLevel.HIGH),

        // R3: 跨地域开锁（同一用户 30min 内在两个城市开锁）
        new GeoJumpRule(30, TimeUnit.MINUTES, RiskLevel.CRITICAL),

        // R4: 退房后开锁（已办理退房，门锁再次被开）
        new PostCheckoutRule(RiskLevel.CRITICAL),

        // R5: 未知身份开锁（无有效预订/授权记录）
        new UnknownIdentityRule(RiskLevel.HIGH),

        // R6: 离线期间开锁记录上报（设备离线时的开锁事件）
        new OfflineUnlockRule(RiskLevel.MEDIUM),

        // R7: 应急钥匙开锁（使用机械钥匙而非电子方式）
        new EmergencyKeyRule(RiskLevel.HIGH)
    );

    public RiskDecision evaluate(UnlockContext ctx) {
        List<RiskHit> hits = new ArrayList<>();

        for (RiskRule rule : rules) {
            RiskHit hit = rule.evaluate(ctx);
            if (hit.isHit()) {
                hits.add(hit);
            }
        }

        // 取最高风险等级
        RiskLevel maxLevel = hits.stream()
            .map(RiskHit::getLevel)
            .max(Comparator.naturalOrder())
            .orElse(RiskLevel.LOW);

        // 生成决策
        return RiskDecision.builder()
            .level(maxLevel)
            .hits(hits)
            .action(resolveAction(maxLevel))
            .build();
    }

    private RiskAction resolveAction(RiskLevel level) {
        return switch (level) {
            case LOW      -> RiskAction.ALLOW;
            case MEDIUM   -> RiskAction.ALLOW_WITH_LOG;   // 放行 + 告警
            case HIGH     -> RiskAction.CHALLENGE;        // 二次验证
            case CRITICAL -> RiskAction.BLOCK;            // 直接拦截
        };
    }
}

3. 多维度评分模型

/** 风险评分模型 — 加权多维评分 */
public class RiskScoreModel {

    public RiskScore calculate(UnlockContext ctx) {
        double score = 0.0; // 0=安全, 100=极危
        Map<String, Double> dimensions = new LinkedHashMap<>();

        // D1: 设备维度（权重 25%）
        double deviceScore = evaluateDeviceRisk(ctx);
        dimensions.put("device", deviceScore);
        score += deviceScore * 0.25;

        // D2: 用户维度（权重 30%）
        double userScore = evaluateUserRisk(ctx);
        dimensions.put("user", userScore);
        score += userScore * 0.30;

        // D3: 环境维度（权重 25%）
        double envScore = evaluateEnvironmentRisk(ctx);
        dimensions.put("environment", envScore);
        score += envScore * 0.25;

        // D4: 行为维度（权重 20%）
        double behaviorScore = evaluateBehaviorRisk(ctx);
        dimensions.put("behavior", behaviorScore);
        score += behaviorScore * 0.20;

        return new RiskScore(score, dimensions);
    }

    private double evaluateDeviceRisk(UnlockContext ctx) {
        double s = 0;
        if (ctx.isDeviceTampered())     s += 40; // 防拆报警
        if (ctx.isLowBattery())         s += 10; // 低电量异常
        if (ctx.isFirmwareOutdated())   s += 15; // 固件过旧
        if (ctx.hasOfflineGap())        s += 20; // 离线空窗期
        return Math.min(s, 100);
    }

    private double evaluateUserRisk(UnlockContext ctx) {
        double s = 0;
        if (!ctx.hasActiveBooking())     s += 50; // 无有效预订
        if (ctx.isExpiredBooking())      s += 40; // 预订已过期
        if (ctx.isBlacklistedUser())     s += 60; // 黑名单用户
        if (ctx.isFirstTimeUser())       s += 10; // 首次使用
        return Math.min(s, 100);
    }

    private double evaluateEnvironmentRisk(UnlockContext ctx) {
        double s = 0;
        if (ctx.isAbnormalTime())        s += 30; // 异常时段
        if (ctx.isGeoAnomaly())          s += 50; // 地理异常
        if (ctx.isNetworkAnomaly())      s += 20; // 网络异常
        return Math.min(s, 100);
    }

    private double evaluateBehaviorRisk(UnlockContext ctx) {
        double s = 0;
        if (ctx.isHighFrequency())       s += 40; // 高频操作
        if (ctx.isUnlockPatternAnomaly()) s += 35; // 开锁模式异常
        if (ctx.isCredentialAnomaly())   s += 30; // 凭证异常
        return Math.min(s, 100);
    }
}

4. 开锁指令拦截流程

开锁指令下发前，必须经过风控评估。高风险指令被拦截后，触发二次验证或人工审核：

/** 开锁指令风控拦截器 */
public class UnlockCommandInterceptor {

    public InterceptResult intercept(UnlockCommand cmd) {
        // 1. 构建风控上下文
        UnlockContext ctx = buildContext(cmd);

        // 2. 规则引擎评估
        RiskDecision decision = riskEngine.evaluate(ctx);

        // 3. 评分模型补充
        RiskScore score = scoreModel.calculate(ctx);

        // 4. 综合决策
        return switch (decision.getAction()) {
            case ALLOW         -> doAllow(cmd, decision, score);
            case ALLOW_WITH_LOG -> doAllowWithAlert(cmd, decision, score);
            case CHALLENGE     -> doChallenge(cmd, decision, score);
            case BLOCK         -> doBlock(cmd, decision, score);
        };
    }

    private InterceptResult doChallenge(UnlockCommand cmd, RiskDecision d, RiskScore s) {
        // 发送二次验证请求到用户手机
        String challengeId = UUID.randomUUID().toString();
        challengeService.sendVerification(cmd.getUserId(), challengeId);
        challengeCache.put(challengeId, cmd, 5, TimeUnit.MINUTES);

        return InterceptResult.challenge(challengeId, d, s);
    }

    private InterceptResult doBlock(UnlockCommand cmd, RiskDecision d, RiskScore s) {
        // 记录拦截事件 + 触发告警
        alertService.sendSecurityAlert(SecurityAlert.builder()
            .type("UNLOCK_BLOCKED")
            .deviceId(cmd.getDeviceId())
            .userId(cmd.getUserId())
            .riskLevel(d.getLevel())
            .riskScore(s.getScore())
            .hits(d.getHits())
            .build());

        return InterceptResult.blocked(d, s);
    }
}

5. 告警升级与联动

风控拦截后，告警按严重等级升级处理：

LOW放行 + 记录——
MEDIUM放行 + 告警站内消息24h 内查看
HIGH二次验证短信 + App Push5min 内验证
CRITICAL拦截 + 锁定 + 人工短信 + 电话 + 邮件实时响应
CRITICAL 级联动
CRITICAL 级告警触发后：1) 立即拦截开锁指令；2) 设备进入锁定状态（仅管理员可解锁）；3) 通知酒店前台/物业；4) 同步推送至公安联网平台（合规要求）；5) 生成安全事件工单，人工复核。
