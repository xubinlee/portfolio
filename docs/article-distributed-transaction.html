分布式事务实战：从理论到生产级方案落地

系统讲解 CAP/BASE 理论、2PC/XA 强一致方案、TCC 补偿事务、Saga 长事务、本地消息表与 MQ 事务消息、Seata 框架 AT/TCC 模式，结合方案选型与生产实践提供完整指南。

﻿

为什么需要分布式事务？

在微服务架构与数据库分库分表场景下，原本在一个数据库事务中完成的业务操作，被拆分到多个独立的服务与数据源中。如何保证跨服务、跨数据源的数据一致性，成为分布式系统的核心挑战。分布式事务就是解决这一问题的技术体系。

典型场景

跨服务转账：扣款服务与加款服务分属不同数据库，需保证要么同时成功，要么同时失败
订单与库存：下单扣库存涉及订单库与库存库，不能出现超卖或少卖
分库分表：按用户 ID 分片后，跨片操作无法依赖单库事务
异构系统：MySQL 写入成功后需同步到 Redis/Elasticsearch，需保证最终一致

一致性模型说明典型方案性能
强一致性操作完成后立即一致，任意时刻读取均为最新值2PC / 3PC / XA低
最终一致性短时间内可能不一致，但最终会达到一致状态TCC / Saga / 本地消息表高
弱一致性不保证何时一致，优先保证可用性最大努力通知最高
会话一致性同一会话内保证读到最新写入Session 粘性中

CAP 定理指出，分布式系统在一致性(C)、可用性(A)、分区容错性(P)三者中只能满足两个。由于网络分区不可避免，实际系统多在 CP（强一致）与 AP（高可用）间权衡。金融场景偏向 CP，互联网业务多用 AP + 最终一致性。

理论基础：CAP 与 BASE

1. CAP 定理

CAP 由 Eric Brewer 提出，是分布式系统的基石理论。它指出：在发生网络分区（Partition）时，系统必须在一致性（Consistency）与可用性（Availability）之间做出选择。

属性含义权衡策略
C 一致性所有节点同一时刻读到相同数据CP 系统：分区时拒绝写入
A 可用性每次请求都能获得响应（不保证最新）AP 系统：分区时允许旧数据
P 分区容错网络分区时系统仍能运行分布式系统必须具备

2. BASE 理论

BASE 是对 CAP 中 AP 的延伸，是大规模互联网系统的实践准则，追求最终一致性而非强一致性。

BASE 核心要素

Basically Available（基本可用）：故障时允许损失部分可用性（响应时间增加、降级服务）
Soft State（软状态）：允许数据存在中间状态，不要求每时每刻一致
Eventually Consistent（最终一致）：数据副本在一段时间后最终达到一致

3. 分布式事务分类

类别代表方案一致性适用场景
刚性事务2PC / 3PC / XA强一致传统金融、单体内跨库
柔性事务-补偿型TCC最终一致高并发金融、电商
柔性事务-消息型本地消息表 / MQ 事务最终一致异步解耦场景
柔性事务-Saga状态机 / 事件编排最终一致长流程业务
柔性事务-尽力而为最大努力通知弱一致对一致性要求低

2PC 与 XA 协议

两阶段提交（2PC, Two-Phase Commit）是经典的强一致性分布式事务方案，由协调者（Coordinator）统一调度所有参与者（Participant）的提交。XA 是 X/Open 组织定义的 2PC 工业标准协议。

1. 两阶段提交流程

阶段一：准备阶段（Prepare）

1. 协调者向所有参与者发送 Prepare 请求，携带事务内容
2. 参与者执行事务操作（写日志、加锁），但不提交
3. 参与者将执行结果（YES/NO）反馈给协调者
4. 若所有参与者均返回 YES，进入阶段二；否则中断事务

阶段二：提交/回滚阶段（Commit/Rollback）

情况 A：所有参与者 YES
  1. 协调者向所有参与者发送 Commit 指令
  2. 参与者正式提交事务并释放资源
  3. 参与者返回 Ack
  4. 协调者完成事务

情况 B：任一参与者 NO 或超时
  1. 协调者向所有参与者发送 Rollback 指令
  2. 参与者回滚事务并释放资源
  3. 参与者返回 Ack
  4. 协调者中断事务

2. MySQL XA 事务实战

-- 跨两个 MySQL 数据库的 XA 事务示例

-- 数据库 A：扣款
XA START 'transfer_001';
UPDATE account SET balance = balance - 100 WHERE user_id = 1;
XA END 'transfer_001';
XA PREPARE 'transfer_001';

-- 数据库 B：加款
XA START 'transfer_001';
UPDATE account SET balance = balance + 100 WHERE user_id = 2;
XA END 'transfer_001';
XA PREPARE 'transfer_001';

-- 两个库都 PREPARE 成功后，统一提交
XA COMMIT 'transfer_001';

-- 若任一库 PREPARE 失败，统一回滚
-- XA ROLLBACK 'transfer_001';

2PC/XA 的缺陷

同步阻塞：准备阶段资源被锁定，期间参与者无法处理其他请求
单点故障：协调者宕机，参与者会一直阻塞
数据不一致：提交阶段部分参与者网络异常，导致部分提交部分未提交
性能差：多次网络往返与日志持久化，TPS 仅为单库的 1/10
不适用微服务：要求参与者支持 XA 协议，多数 NoSQL/消息队列不支持

TCC 补偿事务

TCC（Try-Confirm-Cancel）是一种柔性事务方案，将每个操作拆分为三个阶段：Try（资源预留）、Confirm（确认执行）、Cancel（取消释放）。相比 2PC，TCC 在业务层实现补偿，不长期锁定资源，性能更高。

1. TCC 三阶段详解

阶段职责示例（转账）
Try预留业务资源，做一致性检查冻结金额（扣减可用余额，增加冻结金额）
Confirm确认执行业务，使用预留资源扣减冻结金额（真正扣款）
Cancel取消执行，释放预留资源解冻金额（冻结金额转回可用余额）

2. 账表设计

-- 账户表：增加冻结金额字段
CREATE TABLE account (
  user_id    BIGINT PRIMARY KEY,
  balance    DECIMAL(18,2) NOT NULL COMMENT '可用余额',
  frozen     DECIMAL(18,2) NOT NULL DEFAULT 0 COMMENT '冻结金额',
  version    INT NOT NULL DEFAULT 0 COMMENT '乐观锁版本'
);

-- TCC 事务日志表（保证幂等与悬挂控制）
CREATE TABLE tcc_transaction_log (
  xid           VARCHAR(64) PRIMARY KEY COMMENT '全局事务ID',
  branch_id     VARCHAR(64) NOT NULL COMMENT '分支事务ID',
  business_key  VARCHAR(128) NOT NULL COMMENT '业务键',
  status        TINYINT NOT NULL COMMENT '1-try 2-confirm 3-cancel',
  create_time   DATETIME DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_branch (branch_id)
);

3. TCC 接口实现

@Service
public class AccountTccService {

    @Autowired private AccountMapper accountMapper;
    @Autowired private TccLogMapper tccLogMapper;

    /** Try：冻结金额 */
    public void tryDeduct(String xid, String branchId, Long userId, BigDecimal amount) {
        // 1. 幂等检查：防止 Confirm/Cancel 重复执行
        if (tccLogMapper.exists(branchId)) return;

        // 2. 防悬挂检查：防止 Cancel 先于 Try 执行
        if (tccLogMapper.isCancelled(branchId)) return;

        // 3. 冻结金额（乐观锁）
        int rows = accountMapper.freeze(userId, amount);
        if (rows == 0) throw new RuntimeException("余额不足或并发冲突");

        // 4. 记录 Try 日志
        tccLogMapper.insert(xid, branchId, Status.TRY);
    }

    /** Confirm：真正扣款 */
    public void confirmDeduct(String branchId, Long userId, BigDecimal amount) {
        // 幂等：已 Confirm 直接返回
        if (tccLogMapper.isConfirmed(branchId)) return;

        // 扣减冻结金额
        accountMapper.deductFrozen(userId, amount);

        // 更新日志状态
        tccLogMapper.updateStatus(branchId, Status.CONFIRM);
    }

    /** Cancel：解冻金额 */
    public void cancelDeduct(String branchId, Long userId, BigDecimal amount) {
        // 幂等：已 Cancel 直接返回
        if (tccLogMapper.isCancelled(branchId)) return;

        // 空回滚处理：Try 未执行就收到 Cancel
        if (!tccLogMapper.exists(branchId)) {
            tccLogMapper.insertCancelled(branchId);  // 标记已 Cancel
            return;
        }

        // 解冻金额
        accountMapper.unfreeze(userId, amount);

        // 更新日志状态
        tccLogMapper.updateStatus(branchId, Status.CANCEL);
    }
}

TCC 四大难题与对策

幂等性：Confirm/Cancel 可能被重试，必须保证重复执行结果一致（通过事务日志表判断）
空回滚：Try 未执行却收到 Cancel，需插入"已 Cancel"记录阻止后续 Try
悬挂：Cancel 先于 Try 执行，Try 后资源永久冻结，需 Cancel 时标记阻止 Try
并发控制：Try 与 Confirm/Cancel 可能并发，需乐观锁或状态机控制

Saga 长事务

Saga 将一个长事务拆分为多个本地事务（Ti），每个本地事务都有对应的补偿事务（Ci）。若某一步失败，按相反顺序执行已完成步骤的补偿事务，实现最终一致性。适合业务流程长、参与方多的场景。

1. Saga 两种实现模式

模式说明优缺点
编排式（Choreography）各服务通过事件驱动，监听彼此事件触发下一步去中心化、低耦合；流程不直观、易循环
协调式（Orchestration）中央协调器统一调度各服务执行与补偿流程清晰、易监控；协调器是单点

2. 订单业务 Saga 示例

以"下单"为例，涉及创建订单→扣库存→扣优惠券→支付四步，任一失败需逆向补偿：

正向流程：
  T1: 创建订单          C1: 取消订单
  T2: 扣减库存          C2: 回滚库存
  T3: 扣减优惠券        C3: 返还优惠券
  T4: 调用支付          C4: 退款

执行场景：
  场景 A（成功）：T1 → T2 → T3 → T4
  场景 B（T3失败）：T1 → T2 → T3(失败) → C2 → C1
  场景 C（T4失败）：T1 → T2 → T3 → T4(失败) → C3 → C2 → C1

3. 协调式 Saga 实现（伪代码）

@Service
public class OrderSagaOrchestrator {

    @Autowired private OrderService orderService;
    @Autowired private InventoryService inventoryService;
    @Autowired private CouponService couponService;
    @Autowired private PayService payService;
    @Autowired private SagaLogService sagaLogService;

    public void execute(OrderRequest req) {
        String sagaId = UUID.randomUUID().toString();
        List<SagaStep> executed = new ArrayList<>();

        try {
            // T1: 创建订单
            orderService.create(req);
            executed.add(SagaStep.ORDER);

            // T2: 扣库存
            inventoryService.deduct(req.getSku(), req.getCount());
            executed.add(SagaStep.INVENTORY);

            // T3: 扣优惠券
            couponService.use(req.getCouponId());
            executed.add(SagaStep.COUPON);

            // T4: 支付
            payService.pay(req.getOrderId(), req.getAmount());

        } catch (Exception e) {
            // 逆向补偿（按相反顺序）
            Collections.reverse(executed);
            for (SagaStep step : executed) {
                try {
                    compensate(step, req);
                } catch (Exception ex) {
                    // 补偿失败记录日志，后续重试
                    sagaLogService.recordFailure(sagaId, step, ex);
                }
            }
            throw e;
        }
    }

    private void compensate(SagaStep step, OrderRequest req) {
        switch (step) {
            case COUPON:    couponService.refund(req.getCouponId()); break;
            case INVENTORY: inventoryService.rollback(req.getSku(), req.getCount()); break;
            case ORDER:     orderService.cancel(req.getOrderId()); break;
        }
    }
}

Saga vs TCC 对比

一致性：TCC 在 Try 阶段已预留资源，异常时数据一致；Saga 在补偿前存在短暂不一致
侵入性：TCC 需实现 Try/Confirm/Cancel 三接口；Saga 只需正向 + 补偿两接口
性能：Saga 无预留资源，性能更高
适用：TCC 适合短事务强一致；Saga 适合长流程最终一致

本地消息表与 MQ 事务

消息型事务通过消息队列实现跨服务最终一致性，核心思想是：将本地事务与消息发送原子化绑定，由消息驱动下游服务消费。本地消息表与事务消息是两种主流实现。

1. 本地消息表方案

在业务库中增加一张消息表，将业务操作与消息插入放在同一本地事务，再由后台任务轮询消息表投递到 MQ。

-- 业务库中的消息表
CREATE TABLE local_message (
  id           BIGINT AUTO_INCREMENT PRIMARY KEY,
  business_key VARCHAR(64) NOT NULL COMMENT '业务键',
  topic        VARCHAR(64) NOT NULL COMMENT 'MQ 主题',
  payload      TEXT NOT NULL COMMENT '消息内容',
  status       TINYINT NOT NULL DEFAULT 0 COMMENT '0-待发送 1-已发送 2-失败',
  retry_count  INT NOT NULL DEFAULT 0,
  create_time  DATETIME DEFAULT CURRENT_TIMESTAMP,
  update_time  DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_status (status, create_time)
);
@Service
public class OrderService {

    @Autowired private OrderMapper orderMapper;
    @Autowired private MessageMapper messageMapper;
    @Autowired private RocketMQTemplate mqTemplate;

    @Transactional  // 本地事务保证订单与消息原子性
    public void createOrder(OrderRequest req) {
        // 1. 写业务表
        orderMapper.insert(req);

        // 2. 写消息表（同一事务）
        LocalMessage msg = new LocalMessage();
        msg.setBusinessKey(req.getOrderId());
        msg.setTopic("order-created");
        msg.setPayload(JSON.toJSONString(req));
        msg.setStatus(0);
        messageMapper.insert(msg);
    }
}

// 后台定时任务：扫描待发送消息投递 MQ
@Scheduled(fixedDelay = 5000)
public void sendPendingMessages() {
    List<LocalMessage> list = messageMapper.selectPending(100);
    for (LocalMessage msg : list) {
        try {
            mqTemplate.convertAndSend(msg.getTopic(), msg.getPayload());
            messageMapper.updateStatus(msg.getId(), 1);  // 已发送
        } catch (Exception e) {
            messageMapper.incrRetry(msg.getId());
            if (msg.getRetryCount() >= 5) {
                messageMapper.updateStatus(msg.getId(), 2);  // 失败，告警
            }
        }
    }
}

2. RocketMQ 事务消息

RocketMQ 原生支持事务消息，通过半消息 + 回查机制，无需本地消息表即可实现最终一致性。

1. 生产者发送"半消息"（消费者暂不可见）到 MQ
2. 半消息发送成功后，执行本地事务
3. 本地事务成功 → 发送 Commit，消息对消费者可见
   本地事务失败 → 发送 Rollback，消息删除
4. 若 Commit/Rollback 丢失，MQ 回查生产者本地事务状态
5. 生产者根据事务状态返回 Commit/Rollback
@Service
public class OrderTransactionProducer {

    @Autowired private TransactionMQProducer producer;
    @Autowired private OrderService orderService;

    public void sendOrderMessage(OrderRequest req) {
        Message<String> msg = MessageBuilder
            .withPayload(JSON.toJSONString(req))
            .setHeader("orderId", req.getOrderId())
            .build();

        producer.sendMessageInTransaction(
            "order-created",
            msg,
            req  // 传递给本地事务执行器
        );
    }
}

@Component
public class OrderTransactionListener implements TransactionListener {

    @Autowired private OrderService orderService;

    /** 执行本地事务 */
    @Override
    public LocalTransactionState executeLocalTransaction(Message msg, Object arg) {
        OrderRequest req = (OrderRequest) arg;
        try {
            orderService.createOrder(req);  // 本地事务
            return LocalTransactionState.COMMIT_MESSAGE;
        } catch (Exception e) {
            return LocalTransactionState.ROLLBACK_MESSAGE;
        }
    }

    /** 事务回查（MQ 未收到 Commit/Rollback 时调用） */
    @Override
    public LocalTransactionState checkLocalTransaction(MessageExt msg) {
        String orderId = msg.getUserProperty("orderId");
        // 查询本地事务是否成功
        return orderService.exists(orderId)
            ? LocalTransactionState.COMMIT_MESSAGE
            : LocalTransactionState.ROLLBACK_MESSAGE;
    }
}

消息消费幂等性

消息可能被重复投递，消费者必须保证幂等。常用方案：
唯一键约束：消费时插入带唯一键的记录，重复插入失败即跳过
状态机：业务状态只能单向流转，重复消费时状态已变更直接跳过
Redis 去重：消费前 SETNX 业务键，已存在则跳过

Seata 框架实战

Seata（Simple Extensible Autonomous Transaction Architecture）是阿里巴巴开源的分布式事务解决方案，提供 AT、TCC、Saga、XA 四种模式，是 Java 微服务生态的事实标准。

1. Seata 架构组件

组件职责说明
TC（Transaction Coordinator）事务协调器独立部署，维护全局事务状态，驱动提交/回滚
TM（Transaction Manager）事务管理器定义全局事务边界，开启/提交/回滚
RM（Resource Manager）资源管理器管理分支事务资源，注册分支，上报状态

3. AT 模式实战（推荐）

AT（Auto Transaction）模式是 Seata 最易用的模式，基于本地事务 + undo_log 自动生成反向 SQL 实现补偿，业务零侵入。

-- 每个业务库创建 undo_log 表
CREATE TABLE undo_log (
  branch_id     BIGINT NOT NULL COMMENT '分支事务ID',
  xid           VARCHAR(64) NOT NULL COMMENT '全局事务ID',
  context       VARCHAR(128) NOT NULL,
  rollback_info LONGBLOB NOT NULL COMMENT '回滚数据',
  log_status    INT NOT NULL,
  log_created   DATETIME NOT NULL,
  log_modified  DATETIME NOT NULL,
  UNIQUE KEY ux_undo_log (xid, branch_id)
);

@Service
public class OrderService {

    @Autowired private OrderMapper orderMapper;
    @Autowired private StorageFeignClient storageClient;  // 远程库存服务
    @Autowired private AccountFeignClient accountClient;  // 远程账户服务

    @GlobalTransactional  // 开启全局事务（TM）
    public void createOrder(OrderRequest req) {
        // 分支事务1（RM）：创建订单
        orderMapper.insert(req);

        // 分支事务2（RM）：远程扣库存
        storageClient.deduct(req.getCommodityCode(), req.getCount());

        // 分支事务3（RM）：远程扣款
        accountClient.debit(req.getUserId(), req.getMoney());

        // 任一分支失败，TC 自动驱动所有分支回滚
    }
}

AT 模式执行原理

一阶段：拦截业务 SQL，生成前镜像（before image）与后镜像（after image）存入 undo_log，本地事务提交并释放锁
二阶段-提交：异步删除 undo_log（无需回滚）
二阶段-回滚：根据 undo_log 后镜像与当前数据比对，生成反向 SQL 回滚

4. AT 模式写隔离与读隔离

写隔离：
  - 一阶段提交前，TC 获取全局锁（行级，key=表名+主键）
  - 本地事务提交后释放本地锁，但全局锁保留至二阶段
  - 其他全局事务更新同一行需等待全局锁

读隔离：
  - 默认读已提交（SELECT 走本地快照）
  - @GlobalLock + SELECT FOR UPDATE 可读全局一致性快照

方案选型与对比

不同分布式事务方案各有优劣，需根据业务场景的一致性要求、性能要求、开发成本综合选型。

方案一致性性能侵入性复杂度适用场景
2PC/XA强一致低低中单体内跨库、传统金融
TCC最终一致高高高高并发金融、电商核心
Saga最终一致高中中长流程业务、旅游预订
本地消息表最终一致高中低异步解耦、异构系统
MQ 事务消息最终一致高低低异步解耦、RocketMQ 用户
Seata AT最终一致中低低微服务通用、快速接入
最大努力通知弱一致最高低低支付结果回调

选型决策树

是否要求强一致性？
├─ 是 → 是否单体内跨库？
│       ├─ 是 → 2PC / XA
│       └─ 否 → 微服务强一致？Seata XA 模式
└─ 否 → 最终一致性
        ├─ 业务流程长（>5步）？ → Saga
        ├─ 高并发金融核心？ → TCC
        ├─ 异步解耦场景？
        │   ├─ 用 RocketMQ？ → 事务消息
        │   └─ 其他 MQ？ → 本地消息表
        └─ 通用微服务快速接入？ → Seata AT

选型原则

能用本地事务就不用分布式事务：通过合理的服务拆分与数据库设计，将强一致需求收敛到单库
能用最终一致就不用强一致：互联网业务多可接受短暂不一致，换取高性能
优先消息驱动：消息型方案侵入小、性能高，是异步场景首选
Seata AT 优先：业务无感知、接入成本低，适合大多数微服务场景

4. 兜底补偿机制

// 定时任务扫描补偿失败的事务，人工介入或自动重试
@Scheduled(fixedDelay = 60000)
public void compensateFailedTransactions() {
    List<FailedTx> list = failedTxMapper.selectRetry(50);
    for (FailedTx tx : list) {
        try {
            compensationService.compensate(tx);
            failedTxMapper.markResolved(tx.getId());
        } catch (Exception e) {
            failedTxMapper.incrRetry(tx.getId());
            if (tx.getRetryCount() >= 10) {
                // 超过最大重试次数，告警人工介入
                alertService.notify("分布式事务补偿失败: " + tx.getXid());
            }
        }
    }
}

生产最佳实践

1. 设计原则

原则说明
避免分布式事务通过服务拆分与领域设计，将强一致需求收敛到单库
接口幂等设计所有事务接口必须幂等，支持重试
补偿可重入补偿操作必须可重复执行，结果一致
资源可预留TCC 的 Try 阶段预留资源需有明确业务含义
超时设置全局事务设置合理超时，避免长时间挂起
日志可追溯记录完整事务链路，便于排查与补偿

2. 幂等性实现模板

@Service
public class IdempotentService {

    @Autowired private RedisTemplate redis;

    public void process(Request req) {
        String key = "idempotent:" + req.getBizType() + ":" + req.getBizId();
        // SETNX 设置幂等键，TTL 24 小时
        Boolean acquired = redis.opsForValue()
            .setIfAbsent(key, "1", 24, TimeUnit.HOURS);

        if (Boolean.FALSE.equals(acquired)) {
            // 已处理过，查询结果返回
            return queryResult(req.getBizId());
        }

        try {
            // 执行业务逻辑
            doBusiness(req);
        } catch (Exception e) {
            // 失败删除幂等键，允许重试
            redis.delete(key);
            throw e;
        }
    }
}

3. 异常处理与重试策略

@Retryable(
    value = {NetworkException.class, TimeoutException.class},
    maxAttempts = 3,
    backoff = @Backoff(delay = 1000, multiplier = 2)
)
public void callRemoteService(Request req) {
    // 网络异常自动重试，指数退避
    remoteService.execute(req);
}

@Recover
public void recover(Exception e, Request req) {
    // 重试耗尽后，记录日志并补偿
    log.error("远程调用失败，执行补偿: {}", req, e);
    compensationService.compensate(req);
}

总结与展望

分布式事务是微服务架构下保证数据一致性的关键技术。从强一致的 2PC/XA 到最终一致的 TCC/Saga/消息事务，每种方案都有其适用场景与权衡。掌握 CAP/BASE 理论、理解各方案原理、结合业务选型，是构建可靠分布式系统的基础。

核心要点回顾

理论基石：CAP 三选二，BASE 追求最终一致，互联网系统多选 AP
强一致方案：2PC/XA 性能差、侵入低，适合传统金融单体内跨库
补偿型：TCC 性能高、侵入高，需解决幂等/空回滚/悬挂三大难题
Saga：长事务首选，正向+补偿两接口，适合业务流程多的场景
消息型：本地消息表与事务消息，异步解耦、性能最高
Seata：AT 模式业务零侵入，是微服务快速接入首选
选型原则：能不用就不用，能用最终一致就不用强一致

未来，随着Service Mesh（Istio）将事务能力下沉基础设施、Serverless 简化分布式复杂性、CRDT（无冲突复制数据类型）提供新的最终一致模型，分布式事务的实践将持续演进。作为开发者，建议在掌握现有方案的同时，关注 Dapr、Seata-go 等多语言生态，在实际项目中根据业务特点灵活组合多种方案。
