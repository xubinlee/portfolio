Kubernetes 部署实战：从集群搭建到生产级应用发布

系统讲解 K8s 核心概念、集群环境搭建、应用部署策略、服务网络、持久化存储、配置管理、监控运维与 CI/CD 自动化，结合真实项目案例提供生产级最佳实践。

为什么选择 Kubernetes？

在云原生时代，Kubernetes（简称 K8s）已成为容器编排的事实标准。它最初由 Google 基于内部 Borg 系统的设计理念开源，现由 CNCF 维护，全球拥有最活跃的开源社区之一。K8s 提供了自动化部署、弹性伸缩、负载均衡、服务发现、滚动更新、自愈恢复等核心能力，让企业能够以声明式方式管理大规模容器化应用。

核心优势

声明式配置：通过 YAML 清单描述期望状态，K8s 自动驱动实际状态趋近期望状态，无需手动干预
自愈能力：节点故障时自动迁移 Pod，容器崩溃时自动重启，保障服务高可用
弹性伸缩：基于 CPU/内存/自定义指标的 HPA 自动扩缩容，从容应对流量波动
生态丰富：Helm 包管理、Istio 服务网格、Prometheus 监控、ArgoCD GitOps 等成熟生态

能力维度Kubernetes 原生支持生态扩展方案
容器编排Deployment / StatefulSet / DaemonSetArgo Workflows / Tekton
服务发现Service / CoreDNS / IngressIstio / Linkerd 服务网格
配置管理ConfigMap / SecretVault / External Secrets
持久化存储PV / PVC / StorageClassRook / Longhorn / OpenEBS
监控运维Metrics Server / EventsPrometheus + Grafana
包管理kubectl applyHelm / Kustomize

集群环境搭建

1. 基础环境准备

生产环境推荐使用 kubeadm 初始化集群，它是 Kubernetes 官方维护的引导工具，支持从零搭建符合最佳实践的多节点集群。以下以 Ubuntu 22.04 为例，搭建 1 Master + 2 Worker 的标准集群。

步骤 1.1：系统内核与基础配置

所有节点需执行以下系统级配置，确保内核参数、防火墙、SELinux 满足 K8s 运行要求：

# 关闭 swap（K8s 强制要求）
sudo swapoff -a
sudo sed -i "/ swap / s/^\(.*\)$/#\1/g" /etc/fstab

# 加载必要的内核模块
sudo modprobe br_netfilter
sudo modprobe overlay
cat <<EOF | sudo tee /etc/modules-load.d/k8s.conf
br_netfilter
overlay
EOF

# 配置内核网络参数
cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sudo sysctl --system

# 关闭防火墙（或开放必要端口）
sudo systemctl stop firewalld
sudo systemctl disable firewalld

# 关闭 SELinux
sudo setenforce 0
sudo sed -i "s/^SELINUX=enforcing$/SELINUX=permissive/" /etc/selinux/config

生产安全提示

生产环境不建议直接关闭防火墙，应按官方文档开放以下端口：
Master 节点：6443(API)、2379-2380(etcd)、10250(kubelet)、10259(kube-scheduler)、10257(kube-controller)
Worker 节点：10250(kubelet)、30000-32767(NodePort)

步骤 1.2：安装容器运行时（containerd）

自 Kubernetes 1.24 起，Dockershim 已被移除，推荐使用 containerd 作为容器运行时（CRI）。containerd 性能更优、资源占用更少，且是 CNCF 毕业项目。

# 安装 containerd
sudo apt-get update
sudo apt-get install -y containerd.io

# 生成默认配置
sudo mkdir -p /etc/containerd
containerd config default | sudo tee /etc/containerd/config.toml

# 修改配置：使用 systemd cgroup driver（K8s 推荐）
sudo sed -i "s/SystemdCgroup = false/SystemdCgroup = true/g" /etc/containerd/config.toml

# 配置镜像加速（国内环境必需）
# 在 [plugins."io.containerd.grpc.v1.cri".registry.mirrors] 下添加：
#   [plugins."io.containerd.grpc.v1.cri".registry.mirrors."docker.io"]
#     endpoint = ["https://mirror.ccs.tencentyun.com"]

sudo systemctl restart containerd
sudo systemctl enable containerd

步骤 1.3：安装 kubeadm、kubelet、kubectl

# 添加 Kubernetes apt 源
sudo apt-get install -y apt-transport-https ca-certificates curl gpg
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.30/deb/Release.key | \
  sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo "deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] \
  https://pkgs.k8s.io/core:/stable:/v1.30/deb/ /" | \
  sudo tee /etc/apt/sources.list.d/kubernetes.list

sudo apt-get update
sudo apt-get install -y kubelet kubeadm kubectl
sudo systemctl enable kubelet

2. 初始化控制平面（Master 节点）

# 在 Master 节点执行集群初始化
sudo kubeadm init \
  --apiserver-advertise-address=192.168.1.10 \
  --image-repository=registry.cn-hangzhou.aliyuncs.com/google_containers \
  --kubernetes-version=v1.30.0 \
  --service-cidr=10.96.0.0/12 \
  --pod-network-cidr=10.244.0.0/16 \
  --token-ttl=0

# 配置 kubectl 访问凭证
mkdir -p C:Userslxubin/.kube
sudo cp -i /etc/kubernetes/admin.conf C:Userslxubin/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

# 验证集群状态
kubectl get nodes
kubectl get componentstatuses

参数说明

--apiserver-advertise-address：Master 节点对外可达的 IP 地址
--image-repository：国内镜像仓库地址，解决 gcr.io 拉取超时问题
--service-cidr：Service 虚拟 IP 地址段（ClusterIP 范围）
--pod-network-cidr：Pod 网络地址段，需与 CNI 插件配置一致
--token-ttl=0：Token 永不过期，方便后续多次加入 Worker 节点

3. 安装 Pod 网络插件（CNI）

K8s 集群初始化后，Pod 间跨节点通信依赖 CNI 插件。生产环境推荐 Calico，它基于 BGP 协议实现高效路由，支持网络策略（NetworkPolicy）实现微服务间的网络隔离。

# 安装 Calico（Tigera Operator 方式，推荐）
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.0/manifests/tigera-operator.yaml
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.0/manifests/custom-resources.yaml

# 验证 Calico Pod 运行状态
kubectl get pods -n calico-system -w

# 验证节点就绪
kubectl get nodes

4. 加入 Worker 节点

# 在 Master 初始化输出的 join 命令，在所有 Worker 节点执行：
sudo kubeadm join 192.168.1.10:6443 \
  --token abcdef.0123456789abcdef \
  --discovery-token-ca-cert-hash sha256:xxxx...

# 如果丢失了 join 命令，可在 Master 节点重新生成：
kubeadm token create --print-join-command

# 验证所有节点已加入集群
kubectl get nodes -o wide

核心概念与资源对象

Kubernetes 的设计理念围绕声明式 API展开，所有系统状态通过 API 对象描述。理解以下核心资源对象是掌握 K8s 的基础：

资源对象用途关键属性
Pod最小调度单元，包含一个或多个容器restartPolicy, containers, volumes
Deployment无状态应用管理，控制副本数与滚动更新replicas, strategy, selector
StatefulSet有状态应用管理，稳定网络标识与持久化serviceName, volumeClaimTemplates
DaemonSet每个节点运行一个 Pod 副本nodeSelector, tolerations
Service服务发现与负载均衡type, selector, ports
IngressHTTP 层路由与 TLS 终止rules, tls, ingressClassName
ConfigMap非敏感配置存储data, binaryData
Secret敏感信息加密存储type, data
PV/PVC持久化存储申请与绑定storageClassName, accessModes

Pod 生命周期详解

Pod 是 K8s 中最小的调度单元。它封装了一个或多个容器，共享网络命名空间（IP 地址）和存储卷。理解 Pod 的生命周期对于排查问题至关重要：

# Pod 生命周期阶段：
# Pending -> ContainerCreating -> Running -> Succeeded/Failed
#                     ↳ CrashLoopBackOff (崩溃循环)
#                     ↳ ImagePullBackOff (镜像拉取失败)

# 查看 Pod 状态
kubectl get pods -o wide
kubectl describe pod "my-app-7d4b8f6c5-x2k9j"

# 查看 Pod 事件（排查关键）
kubectl get events --field-selector involvedObject.name="my-app-7d4b8f6c5-x2k9j"

# 查看容器日志
kubectl logs my-app-7d4b8f6c5-x2k9j --previous  # 查看上一次崩溃的日志
kubectl logs my-app-7d4b8f6c5-x2k9j -c sidecar    # 指定容器日志

应用部署实战

1. Deployment 无状态应用

Deployment 是 K8s 中最常用的工作负载类型，适用于 Web 服务、API 网关等无状态应用。它通过 ReplicaSet 管理 Pod 副本，支持滚动更新和回滚操作。

apiVersion: apps/v1
kind: Deployment
metadata:
  name: lxb-gateway
  namespace: production
  labels:
    app: lxb-gateway
    version: v3.7.0
spec:
  replicas: 3
  revisionHistoryLimit: 5
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # 滚动更新时最多超出副本数 1 个
      maxUnavailable: 0   # 滚动更新时不允许不可用 Pod
  selector:
    matchLabels:
      app: lxb-gateway
  template:
    metadata:
      labels:
        app: lxb-gateway
    spec:
      terminationGracePeriodSeconds: 60
      containers:
      - name: gateway
        image: registry.cn-hangzhou.aliyuncs.com/lxb/lxb-gateway:3.7.0
        ports:
        - containerPort: 9999
          protocol: TCP
        env:
        - name: NACOS_HOST
          valueFrom:
            configMapKeyRef:
              name: lxb-config
              key: nacos.host
        - name: JAVA_OPTS
          value: "-Xms512m -Xmx512m -XX:+UseG1GC"
        resources:
          requests:
            cpu: "500m"
            memory: "512Mi"
          limits:
            cpu: "2000m"
            memory: "2Gi"
        livenessProbe:
          httpGet:
            path: /actuator/health/liveness
            port: 9999
          initialDelaySeconds: 60
          periodSeconds: 15
          failureThreshold: 3
        readinessProbe:
          httpGet:
            path: /actuator/health/readiness
            port: 9999
          initialDelaySeconds: 30
          periodSeconds: 10
          failureThreshold: 3
        volumeMounts:
        - name: logs
          mountPath: /app/logs
      volumes:
      - name: logs
        emptyDir: {}

2. StatefulSet 有状态应用

对于数据库、消息队列等需要稳定网络标识和持久化存储的应用，必须使用 StatefulSet。它保证 Pod 按顺序创建/删除，并提供稳定的 DNS 名称。

apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
  namespace: production
spec:
  serviceName: mysql-headless  # 必须指定 Headless Service
  replicas: 3
  selector:
    matchLabels:
      app: mysql
  template:
    metadata:
      labels:
        app: mysql
    spec:
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                app: mysql
            topologyKey: "kubernetes.io/hostname"  # Pod 分散到不同节点
      containers:
      - name: mysql
        image: mysql:8.0
        ports:
        - containerPort: 3306
        env:
        - name: MYSQL_ROOT_PASSWORD
          valueFrom:
            secretKeyRef:
              name: mysql-secret
              key: root-password
        volumeMounts:
        - name: data
          mountPath: /var/lib/mysql
  volumeClaimTemplates:     # 每个 Pod 自动创建一个 PVC
  - metadata:
      name: data
    spec:
      storageClassName: local-storage
      accessModes: [ "ReadWriteOnce" ]
      resources:
        requests:
          storage: 50Gi

StatefulSet vs Deployment

网络标识：StatefulSet Pod 拥有稳定的 DNS 名称（mysql-0.mysql-headless），Deployment Pod 名称随机
启动顺序：StatefulSet 按序号创建 Pod，确保前一个就绪后才启动下一个
持久化：StatefulSet 通过 volumeClaimTemplates 为每个 Pod 绑定独立 PVC，不会因 Pod 重建而丢失

3. 滚动更新与回滚

K8s Deployment 的滚动更新策略确保服务零平稳过渡，配合 readinessProbe 可实现真正的零平滑部署：

# 滚动更新：修改镜像版本触发
kubectl set image deployment/lxb-gateway gateway=lxb/lxb-gateway:3.7.1 -n production

# 查看滚动更新状态
kubectl rollout status deployment/lxb-gateway -n production

# 查看历史版本
kubectl rollout history deployment/lxb-gateway -n production

# 回滚到上一个版本
kubectl rollout undo deployment/lxb-gateway -n production

# 回滚到指定版本
kubectl rollout undo deployment/lxb-gateway --to-revision=2 -n production

# 暂停滚动更新（用于金丝雀发布）
kubectl rollout pause deployment/lxb-gateway -n production
kubectl rollout resume deployment/lxb-gateway -n production

4. HPA 自动扩缩容

基于 CPU/内存使用率或自定义指标，HPA 自动调整 Pod 副本数，应对流量波动：

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: lxb-gateway-hpa
  namespace: production
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: lxb-gateway
  minReplicas: 3
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70    # CPU 使用率超过 70% 触发扩容
  - type: Resource
    resource:
      name: memory
      target:
        type: Utilization
        averageUtilization: 80    # 内存使用率超过 80% 触发扩容
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300  # 缩容冷却期 5 分钟
      policies:
      - type: Percent
        value: 10
        periodSeconds: 60
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
      - type: Percent
        value: 100
        periodSeconds: 15
      - type: Pods
        value: 4
        periodSeconds: 60
      selectPolicy: Max

服务发现与网络配置

1. Service 服务暴露

K8s Service 为 Pod 提供稳定的访问入口，通过 label selector 自动关联后端 Pod。常用的 Service 类型包括：

apiVersion: v1
kind: Service
metadata:
  name: lxb-gateway-svc
  namespace: production
spec:
  type: ClusterIP       # 集群内部访问（默认类型）
  # type: NodePort      # 通过节点端口暴露（30000-32767）
  # type: LoadBalancer  # 云环境自动创建外部负载均衡器
  selector:
    app: lxb-gateway
  ports:
  - name: http
    port: 80           # Service 监听端口
    targetPort: 9999   # Pod 容器端口
    protocol: TCP
  sessionAffinity: ClientIP  # 会话亲和，同一客户端请求转发到同一 Pod
---
# Headless Service（用于 StatefulSet）
apiVersion: v1
kind: Service
metadata:
  name: mysql-headless
spec:
  clusterIP: None       # 不分配 ClusterIP
  selector:
    app: mysql
  ports:
  - port: 3306

2. Ingress HTTP 路由

Ingress 提供了 HTTP 层的路由规则，支持域名路由、TLS 终止、路径分发等能力，是微服务对外暴露的标准方式：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: lxb-ingress
  namespace: production
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "600"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "600"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - api.lxb.vip
    secretName: lxb-tls-secret
  rules:
  - host: api.lxb.vip
    http:
      paths:
      - path: /auth
        pathType: Prefix
        backend:
          service:
            name: lxb-auth-svc
            port:
              number: 3000
      - path: /admin
        pathType: Prefix
        backend:
          service:
            name: lxb-admin-svc
            port:
              number: 3001
      - path: /
        pathType: Prefix
        backend:
          service:
            name: lxb-gateway-svc
            port:
              number: 80

3. NetworkPolicy 网络策略

默认情况下，K8s 集群内所有 Pod 可以互相访问。在生产环境中，必须通过 NetworkPolicy 实现微服务间的网络隔离，遵循最小权限原则：

# 仅允许网关 Pod 访问认证服务
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-gateway-to-auth
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: lxb-auth
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: lxb-gateway    # 仅允许网关访问
    ports:
    - protocol: TCP
      port: 3000
---
# 禁止数据库 Pod 的外部访问
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: deny-external-to-mysql
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: mysql
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector: {}       # 仅允许同命名空间内的 Pod 访问

持久化存储方案

1. StorageClass 动态供应

StorageClass 实现了存储的动态供应，开发者只需申请 PVC，K8s 自动创建 PV。生产环境常用的存储后端包括 Ceph、NFS、Longhorn 等：

# NFS StorageClass 示例
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: nfs-storage
provisioner: nfs.csi.k8s.io
parameters:
  server: 192.168.1.100
  share: /data/nfs
reclaimPolicy: Retain          # 删除 PVC 后保留数据
volumeBindingMode: WaitForFirstConsumer
mountOptions:
  - hard
  - nfsvers=4.1
---
# 申请存储卷
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data-pvc
  namespace: production
spec:
  storageClassName: nfs-storage
  accessModes:
  - ReadWriteMany          # 多节点读写（NFS 特性）
  resources:
    requests:
      storage: 20Gi

2. 存储访问模式

访问模式缩写说明
ReadWriteOnce (RWO)RWO单节点读写，常用于数据库
ReadOnlyMany (ROX)ROX多节点只读，常用于配置文件共享
ReadWriteMany (RWX)RWX多节点读写，需 NFS/CephFS 等分布式文件系统
ReadWriteOncePodRWOP单 Pod 读写（K8s 1.22+）

配置与密钥管理

1. ConfigMap 配置管理

ConfigMap 用于存储非敏感的配置数据，可以作为环境变量、配置文件或命令行参数注入到 Pod 中：

apiVersion: v1
kind: ConfigMap
metadata:
  name: lxb-config
  namespace: production
data:
  application.yml: |
    spring:
      datasource:
        url: jdbc:mysql://mysql:3306/lxb
        username: root
      redis:
        host: redis-master
        port: 6379
  nacos.host: "nacos-server"
  log.level: INFO
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: lxb-admin
spec:
  template:
    spec:
      containers:
      - name: admin
        image: lxb/lxb-admin:3.7.0
        envFrom:
        - configMapRef:
            name: lxb-config    # 注入所有 key-value 为环境变量
        volumeMounts:
        - name: config
          mountPath: /app/config/application.yml
          subPath: application.yml
      volumes:
      - name: config
        configMap:
          name: lxb-config

2. Secret 密钥管理

Secret 用于存储敏感信息（密码、证书、Token 等），数据以 Base64 编码存储。生产环境建议集成 HashiCorp Vault 或 External Secrets Operator 实现动态密钥管理：

# 创建 Docker Registry Secret（拉取私有镜像必需）
kubectl create secret docker-registry aliyun-registry \
  --docker-server=registry.cn-hangzhou.aliyuncs.com \
  --docker-username=admin@lxb \
  --docker-password=PASSWORD \
  --docker-email=admin@lxb.vip \
  -n production

# 创建 TLS Secret（Ingress HTTPS 必需）
kubectl create secret tls lxb-tls-secret \
  --cert=fullchain.pem \
  --key=privkey.pem \
  -n production

# 查看 Secret（仅显示 Base64 编码）
kubectl get secret lxb-config -n production -o yaml

# 解码查看 Secret 内容
kubectl get secret lxb-config -n production \
  -o jsonpath="{.data.password}" | base64 -d

监控与日志体系

1. Prometheus + Grafana 监控堆栈

使用 kube-prometheus-stack Helm Chart 一键部署完整监控方案，包含 Prometheus、Grafana、AlertManager、Node Exporter 等组件：

# 添加 Helm 仓库
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

# 部署 kube-prometheus-stack
helm install monitoring prometheus-community/kube-prometheus-stack \
  --namespace monitoring \
  --create-namespace \
  --set prometheus.service.type=NodePort \
  --set prometheus.service.nodePort=30090 \
  --set grafana.service.type=NodePort \
  --set grafana.service.nodePort=30030 \
  --set grafana.adminPassword=lxb@2026

# 获取 Grafana 初始密码
kubectl get secret -n monitoring monitoring-grafana \
  -o jsonpath="{.data.admin-password}" | base64 -d

# 访问 Grafana
# http://NODE_IP:30030  admin/lxb@2026

2. 自定义监控指标

通过 Prometheus ServiceMonitor 自动发现应用的 /actuator/prometheus 端点，采集 Spring Boot Actuator 暴露的业务指标：

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: lxb-services
  namespace: production
  labels:
    release: monitoring
spec:
  selector:
    matchLabels:
      monitoring: enabled
  endpoints:
  - port: metrics          # 对应 Service 的 named port
    path: /actuator/prometheus
    interval: 15s
    scrapeTimeout: 10s
  namespaceSelector:
    matchNames:
    - production

CI/CD 自动化部署

1. GitOps 与 ArgoCD

GitOps 是现代云原生应用部署的最佳实践，Git 仓库作为应用期望状态的唯一真理来源。ArgoCD 持续监听 Git 仓库，自动同步到集群：

# 部署 ArgoCD
kubectl create namespace argocd
kubectl apply -n argocd \
  -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# 获取 ArgoCD 初始密码
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d

# 通过 CLI 登录
argocd login argocd.lxb.vip \
  --username admin \
  --password PASSWORD

# 注册集群凭证（多集群管理必需）
argocd cluster add production-cluster

2. ArgoCD Application 声明

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: lxb-production
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://git.lxb.vip/devops/lxb-k8s-manifests.git
    targetRevision: main
    path: overlays/production
  destination:
    server: https://kubernetes.default.svc
    namespace: production
  syncPolicy:
    automated:
      prune: true           # 自动删除 Git 中已移除的资源
      selfHeal: true        # 自动修复手动修改
    syncOptions:
    - CreateNamespace=true
    - PruneLast=true
  revisionHistoryLimit: 10

3. Kustomize 多环境配置

Kustomize 允许为不同环境（dev/staging/prod）定义差异配置，避免 YAML 重复：

# base/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: lxb-gateway
spec:
  replicas: 1
  template:
    spec:
      containers:
      - name: gateway
        image: lxb/lxb-gateway:latest
---
# overlays/production/kustomization.yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
namespace: production
resources:
- ../../base
patches:
- replica_count.yaml
images:
- name: lxb/lxb-gateway
  newTag: 3.7.0
configMapGenerator:
- name: lxb-config
  literals:
  - ENV=production
  - LOG_LEVEL=INFO

生产最佳实践

1. 资源配额与限制

生产环境必须为每个 Pod 设置 resource requests/limits，并在命名空间级别配置 ResourceQuota 和 LimitRange：

# 命名空间资源配额
apiVersion: v1
kind: ResourceQuota
metadata:
  name: production-quota
  namespace: production
spec:
  hard:
    requests.cpu: "20"
    requests.memory: 40Gi
    limits.cpu: "40"
    limits.memory: 80Gi
    persistentvolumeclaims: "10"
    pods: "50"
---
# 默认资源限制
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
  namespace: production
spec:
  limits:
  - type: Container
    default:          # 默认 limits
      cpu: "1000m"
      memory: 1Gi
    defaultRequest:   # 默认 requests
      cpu: "200m"
      memory: 256Mi
    max:              # 最大限制
      cpu: "4000m"
      memory: 8Gi

2. Pod 安全上下文

遵循最小权限原则，禁止容器以 root 运行，限制文件系统访问权限：

spec:
  securityContext:
    runAsNonRoot: true       # 禁止 root 用户运行
    runAsUser: 1000          # 指定运行用户 UID
    fsGroup: 2000            # 卷挂存储卷的组 GID
    seccompProfile:
      type: RuntimeDefault   # 启用默认系统调用过滤
  containers:
  - name: app
    securityContext:
      allowPrivilegeEscalation: false  # 禁止提权
      readOnlyRootFilesystem: true     # 只读根文件系统
      capabilities:
        drop: [ALL]                    # 丢弃所有 Linux capabilities

3. 多集群管理

对于核心业务，建议采用多集群架构实现容灾恢复。通过 Karmada 或 Cluster API 管理多个 K8s 集群，实现跨集群应用调度：

生产检查清单

集群高可用：至少 3 个 Master 节点，etcd 启用 TLS 加密并定期备份
资源配额：所有 Pod 设置 requests/limits，命名空间配置 ResourceQuota
网络隔离：通过 NetworkPolicy 实现微服务间的访问控制
密钥管理：使用 Vault 或 External Secrets 动态管理密钥，禁止硬编码
监控告警：Prometheus AlertManager 配置关键指标告警，推送到企业微信/钉钉
日志集中：Loki + Fluent Bit 实现日志统一采集与查询
自动化部署：GitOps + ArgoCD 实现声明式自动化发布

总结与展望

Kubernetes 作为云原生时代的基础设施，已经成为企业容器化转型的标准选择。掌握 K8s 不仅需要理解核心概念和资源对象，更需要在实战中积累运维经验。

核心要点回顾

集群搭建：kubeadm + containerd + Calico 是生产环境的标准组合
应用部署：Deployment 适用于无状态服务，StatefulSet 适用于数据库等有状态应用
网络通信：Service + Ingress 实现服务发现与外部访问，NetworkPolicy 实现网络安全隔离
持久化：StorageClass + PVC 实现存储动态供应，支持 NFS/Ceph/Longhorn 等后端
配置管理：ConfigMap + Secret 分离配置与密钥，结合 Vault 实现动态密钥管理
监控运维：Prometheus + Grafana + Loki 构建完整可观测性体系
自动化：GitOps + ArgoCD + Kustomize 实现声明式自动化发布

未来，K8s 生态将继续向服务网格（Istio）、Serverless（Knative）、边缘计算（KubeEdge）等方向演进。作为开发者，建议在掌握基础的同时，持续关注社区动态，在实际项目中不断实践与优化。
