🚀 海量设备并发处理

几万台智能锁同时上报指纹、开门记录、电量、告警 — 消息堆积怎么处理，从接入层到存储层的全链路优化实践。

并发场景分析与量化

1. 智能锁数据上报模型

一台智能锁在运行过程中会产生多种类型的上报数据，各类型数据特征差异巨大：

数据类型频率单条大小QoS可靠性要求
心跳保活1次/60s~50BQoS 0可丢失
开门记录事件驱动（~5次/天）~200BQoS 1不可丢，可重复
指纹上报事件驱动（注册时）~2KBQoS 1不可丢，可重复
电量上报1次/小时~80BQoS 0可丢失
告警事件事件驱动（低频）~300BQoS 1不可丢，需即时

2. 峰值估算

📌 峰值计算公式
稳态 QPS = 设备数 × 平均每秒消息数
峰值 QPS = 稳态 QPS × 峰值倍数（通常 3~10 倍）

3 万台设备场景：
• 稳态心跳：30000 / 60 = 500 msg/s
• 稳态开门：30000 × 5 / 86400 ≈ 1.7 msg/s
• 网络恢复峰值（3 倍）：1500 + 离线积压数据 ≈ 5000~10000 msg/s

2. Rule Engine 消息分流

利用 EMQX Rule Engine 的 SQL 规则，将不同类型消息分流到不同 Kafka Topic，实现零代码桥接：

-- 开门记录 → Kafka iot-lock-events
SELECT
    payload.mac as mac,
    payload.operation as operation,
    payload.unlockType as unlockType,
    payload.timestamp as eventTime
FROM "/hotel/gateway/publish"
WHERE payload.operation = 'unlock'

-- 告警事件 → Kafka iot-lock-alerts（独立 Topic，高优先级消费）
SELECT *
FROM "/hotel/gateway/publish"
WHERE payload.type = 'alert'

-- 心跳 → Kafka iot-lock-heartbeat（低优先级）
SELECT clientid, timestamp
FROM "/hotel/gateway/alive"

缓冲层：Kafka 分区策略与消费组

1. 分区策略

📌 分区设计原则
Kafka 分区数 = 消费者最大并行度。分区 Key 选择需保证：同一设备的消息路由到同一分区（保证顺序性），同时不同设备均匀分布（保证负载均衡）。
Topic分区数分区 Key保留时间说明
iot-lock-events12${mac}7 天开门记录，按设备路由
iot-lock-alerts6${mac}30 天告警事件，高优先级
iot-lock-heartbeat6${mac}1 天心跳，短保留
iot-lock-dead-letter3Round-Robin30 天死信队列，人工排查

2. 消费组设计

@Configuration
public class KafkaConsumerConfig {

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, String> batchFactory() {
        ConcurrentKafkaListenerContainerFactory<String, String> factory =
            new ConcurrentKafkaListenerContainerFactory<>();
        factory.setConsumerFactory(consumerFactory());
        factory.setBatchListener(true);        // 批量消费
        factory.setConcurrency(6);                  // 6 个消费线程
        factory.getContainerProperties().setAckMode(
            ContainerProperties.AckMode.MANUAL_IMMEDIATE   // 手动提交
        );
        return factory;
    }

    @Bean
    public ConsumerFactory<String, String> consumerFactory() {
        Map<String, Object> props = new HashMap<>();
        props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "kafka:9092");
        props.put(ConsumerConfig.GROUP_ID_CONFIG, "iot-lock-consumer");
        props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 500);  // 每批最多 500 条
        props.put(ConsumerConfig.FETCH_MIN_BYTES_CONFIG, 1024); // 最少 1KB 才返回
        props.put(ConsumerConfig.FETCH_MAX_WAIT_MS_CONFIG, 500); // 最多等 500ms
        return new DefaultKafkaConsumerFactory<>(props);
    }
}

3. 批量写入优化

@Component
public class LockEventConsumer {

    @KafkaListener(topics = "iot-lock-events",
        concurrency = "6", containerFactory = "batchFactory")
    public void consume(List<ConsumerRecord<String, String>> records,
                       Acknowledgment ack) {
        // 1. 反序列化
        List<LockEvent> events = records.stream()
            .map(r -> JSON.parseObject(r.value(), LockEvent.class))
            .collect(Collectors.toList());

        // 2. 幂等去重：Redis Bitmap
        List<LockEvent> deduped = events.stream()
            .filter(e -> checkAndMarkIdempotent(e))
            .collect(Collectors.toList());

        // 3. 批量写 TDengine
        if (!deduped.isEmpty()) {
            tdEngineTemplate.batchInsert("lock_events", deduped);
        }

        // 4. 更新 Redis 热数据
        updateRedisHotData(deduped);

        // 5. 手动提交 offset
        ack.acknowledge();
    }

    private boolean checkAndMarkIdempotent(LockEvent e) {
        String key = "lock:events:idempotent:" + e.getMac();
        return redisTemplate.opsForValue().setIfAbsent(
            key + ":" + e.getSeq(), "1", 24, TimeUnit.HOURS
        );
    }
}

背压与降级策略

1. Kafka 天然背压

Kafka 的消费模型天然实现了背压：消费者按自身节奏拉取消息，Broker 不会推送。当消费者处理慢时，消息堆积在 Kafka 中，不会压垮下游。

📌 背压机制
max.poll.records=500 + max.poll.interval.ms=300000：消费者每次最多拉 500 条，5 分钟内必须处理完并提交。超时则触发 Rebalance，将分区分配给其他消费者。

2. 多级降级策略

L1🟢 正常所有消息正常处理，Kafka Lag < 1000全量处理
L2🟡 降级Lag > 10000，心跳消息只更新 Redis 不写 DB，电量消息降频降级处理
L3🔴 熔断Lag > 100000，暂停低优先级消费组，只保留告警和开门记录熔断保护

降级控制代码

@Component
public class ConsumerDegradationManager {

    @Scheduled(fixedRate = 10000)  // 每 10s 检查一次
    public void checkLagAndAdjust() {
        long lag = kafkaAdmin.getConsumerGroupLag("iot-lock-consumer");

        if (lag > 100000) {
            // L3 熔断：暂停心跳消费组
            consumerManager.pause("iot-lock-heartbeat");
            log.warn("熔断：暂停心跳消费，Lag={}", lag);
        } else if (lag > 10000) {
            // L2 降级：跳过电量写入
            degradationContext.setSkipBattery(true);
            log.warn("降级：跳过电量写入，Lag={}", lag);
        } else {
            // L1 恢复
            consumerManager.resume("iot-lock-heartbeat");
            degradationContext.setSkipBattery(false);
        }
    }
}

幂等保障与消息去重

1. 幂等设计

MQTT QoS 1 存在消息重复的可能，Kafka 消费者 Rebalance 也会导致重复消费。因此消费端必须实现幂等：

🔑 设备序列号
门锁每条消息携带自增 seq，云端用 Redis Bitmap 去重
SETBIT lock:events:{mac} {seq} 1
📋 Kafka Offset
手动提交 offset，处理成功才提交。Rebalance 后从上次提交位置重新消费
💾 数据库唯一约束
TDengine 利用 ts + mac 联合唯一性，MySQL 利用 UNIQUE KEY(device_id, seq)

📌 一句话总结
海量设备并发的核心解法：EMQX 集群水平扩展 + Rule Engine 零代码分流 + Kafka 削峰填谷 + 分层存储 + 批量消费去重。不要在应用层硬限流，把缓冲和背压交给 Kafka。
